# Матрица проверок

Применять правила к фактическим необработанным телам ответов. В примерах `$` означает корень после допустимого снятия единственной оболочки `data`.

## Оба источника

| ID | Проверка | Ожидание | Типичная серьёзность |
|---|---|---|---|
| T01 | HTTP-статус | `2xx` | BLOCKER/HIGH |
| T02 | Тип содержимого | JSON, согласованный с документацией | HIGH/MEDIUM |
| T03 | Парсинг | Однократно сериализованный валидный JSON | BLOCKER |
| T04 | Время ответа | В пределах известного SLA; без SLA сообщать только измерение | INFO/MEDIUM |
| C01 | Верхний уровень | Ожидаемая форма напрямую либо в единственной оболочке `data` | HIGH |
| C02 | Стабильность полей | Нет конкурирующих полей `data`/`Data`, `amount`/`Amount` | HIGH/MEDIUM |
| C03 | Пустой набор | Допустим только если контракт разрешает; не считать дефектом без основания | INFO/MEDIUM |
| C04 | Лишние поля | Фиксировать как INFO, если они не конфликтуют и контракт их не запрещает | INFO |

## Источник 1 — `$.transactions[*]`

| ID | Поле | Проверка | Влияние |
|---|---|---|---|
| S1-01 | `transactions` | Обязательный массив | Расчёт останавливается |
| S1-02 | элемент | Ненулевой JSON-объект | Расчёт останавливается |
| S1-03 | `type` | Строка; ожидаемые значения документированы; `paid` в точном регистре учитывается клиентом | Иной регистр может молча исключить оплату |
| S1-04 | `amount` | JSON number, конечное в среде потребителя; не numeric string | Строка вызывает ошибку клиента |
| S1-05 | `amount` | Проверить отрицательные и нулевые значения относительно доменного контракта | Может исказить доход; без контракта это гипотеза |
| S1-06 | `amount` | Разумная точность и масштаб; научная запись не ошибочна сама по себе | Риск округления/выброса |
| S1-07 | `currency` | Непустая строка, ровно три ASCII-буквы без внешних пробелов | Ошибка курса или скрытая нормализация |
| S1-08 | `currency` | Верхний регистр и актуальный код ISO 4217/поддерживаемый код | Несогласованный контракт/нет курса |
| S1-09 | объект | Повторяющиеся идентификаторы, если идентификатор предоставлен | Возможный двойной учёт |

Проверять `type` у всех элементов, включая неоплаченные. Полную проверку `amount` и `currency` выполнять для всех элементов и отдельно указывать, затрагивает ли дефект транзакции `paid`. Некорректность в неоплаченной записи может быть контрактным дефектом, даже если текущий клиент пропускает её до проверки суммы.

## Источник 2 — `$[*]`

| ID | Проверка | Ожидание | Влияние |
|---|---|---|---|
| S2-01 | Верхний уровень | Массив | Расчёт останавливается |
| S2-02 | Тип элемента | Строка | Расчёт останавливается |
| S2-03 | Токены | После `trim` и разделения по whitespace ровно 2 токена | Иначе элемент не читается |
| S2-04 | Исходный пробел | Рекомендуется один ASCII-пробел, без начальных/конечных пробелов | Клиент терпит, но контракт нестабилен |
| S2-05 | Сумма | Строгая десятичная запись, преобразуется в конечное число | `NaN`/бесконечность/ошибка |
| S2-06 | Сумма | Запрет неоднозначных форматов: разделители тысяч, запятая как десятичный знак, знак валюты | Неверное чтение или отказ |
| S2-07 | Сумма | Отрицательные/нулевые значения сверять с доменным контрактом | Возможное искажение дохода |
| S2-08 | Валюта | Ровно три ASCII-буквы, верхний регистр, актуальный код | Нет курса/контрактная неточность |
| S2-09 | Дубли | Точное повторение строки сообщать отдельно; не утверждать двойной учёт без ID | Возможный дубль |

Для строгой проверки суммы предпочтителен шаблон `^[+-]?(?:0|[1-9]\d*)(?:\.\d+)?$`, но знак и допустимое число знаков после точки определяются доменным контрактом. Значения вроде `1e3` могут преобразоваться JavaScript-клиентом, однако должны быть отмечены как нестабильное представление, если контракт обещает обычную десятичную запись.

## Unicode и нормализация

Проверять и показывать code point для невидимых или похожих символов:

- NBSP `U+00A0`, узкий NBSP `U+202F`, zero-width space `U+200B`;
- кириллические символы, визуально похожие на латинские в коде валюты;
- Unicode minus `U+2212` вместо ASCII `-`;
- управляющие символы и переносы строк внутри значений.

Не вставлять невидимый символ в отчёт без пояснения. Представлять его как `<U+XXXX>`.

## Согласованность и агрегаты

Считать и включать в отчёт:

- число элементов в каждом источнике;
- число `paid` в источнике 1 с учётом точного и без учёта регистра;
- распределение исходных и нормализованных кодов валют;
- минимальную, максимальную и суммарную сумму только для валидно разобранных элементов;
- число элементов, исключённых из агрегатов из-за дефектов;
- точные дубли и основание их определения.

Не смешивать валидные суммы с невалидными ради общей суммы. Не сравнивать итог источников как обязанный совпадать, если API не обещает одинаковый набор операций.

## Формулировка результата

Для каждой находки создавать связку:

`наблюдение → доказательство → влияние → рекомендация → критерий приёмки`.

Пример: «В `source1 $.transactions[4].currency` получено `usd`; клиент нормализует его в `USD`, поэтому текущий расчёт продолжается, но контракт зависит от поведения потребителя. Возвращать ISO-код в верхнем регистре. Критерий: все `currency` соответствуют `^[A-Z]{3}$` до клиентской нормализации».
