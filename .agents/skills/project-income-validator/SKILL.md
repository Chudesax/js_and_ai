# Проверка текущих финансовых API-ответов

Проверять сырые ответы обоих источников до нормализации и финансового расчёта. Цель — зафиксировать наблюдаемые дефекты на стороне API и передать backend-команде воспроизводимый отчёт. Не исправлять и не нормализовывать исходные данные молча.

## Границы ответственности

- Проверять `GET /api/finance1` и `GET /api/finance2` одного базового финансового API.
- Считать ожидаемым контрактом проекта:
  - источник 1: объект или оболочка `{ data: object }`, внутри `transactions: array`;
  - элемент источника 1: объект с `type`, `amount`, `currency`;
  - источник 2: массив или оболочка `{ data: array }`;
  - элемент источника 2: строка строго смыслового формата `<сумма> <валюта>`, например `300 EUR`.
- Проверять исходные значения до клиентских преобразований `trim()`, `toUpperCase()` и `Number()`.
- Не проверять здесь результат `dailySalaryCalc`, UI, агрегаты или CurrencyFreaks, кроме точечной проверки существования валюты при анализе подозрительного кода.
- Не менять backend, клиентские данные, конфигурацию или production-состояние. Выполнять только чтение и создавать локальные артефакты отчёта.

## Обязательная последовательность

### 1. Подготовить безопасный запрос

1. Найти текущие URL, методы и способ авторизации в проекте. Не копировать значения секретов в отчёт или вывод.
2. Использовать существующий запрос приложения либо выполнить эквивалентные read-only запросы.
3. Запрашивать оба источника максимально близко по времени. Запускать независимые запросы параллельно, если это не мешает фиксации метаданных.
4. Зафиксировать для каждого источника:
   - UTC-время начала и окончания;
   - URL без секретных query-параметров;
   - метод;
   - HTTP-статус;
   - `Content-Type`;
   - длительность;
   - размер тела;
   - идентификатор запроса/трассировки из заголовков, если он есть и не содержит секретов.
5. Никогда не показывать API-ключи, токены, cookies и заголовки авторизации. Заменять их на `[REDACTED]` ещё до сохранения артефакта.

Если один запрос не выполнен, всё равно проверить второй и создать отчёт. Сетевую ошибку, таймаут, TLS/CORS, не-2xx статус или не-JSON тело оформить отдельной находкой.

### 2. Сохранить доказательный снимок

Сохранить неизменённые тела ответов во временные файлы вне исходного кода. Не коммитить их автоматически. Если ответы содержат персональные, платёжные или иные чувствительные данные, сохранить только минимальные отредактированные фрагменты, хеш полного тела и агрегаты.

Для каждого снимка вычислить SHA-256. В отчёте указать хеш, время и размер, чтобы backend-команда могла сопоставить проверку с логами. Не заменять исходный снимок нормализованной копией.

### 3. Проверить транспорт и оболочку

Проверить независимо для каждого источника:

- успешный HTTP-статус и стабильный JSON `Content-Type`;
- тело является валидным JSON, а не HTML/текстом ошибки;
- отсутствие неожиданной двойной сериализации JSON;
- ожидаемую верхнеуровневую форму;
- согласованность прямого ответа и оболочки `data`;
- отсутствие неожиданных `null`, дублирующих полей с разным регистром и признаков частичного ответа.

### 4. Проверить контракт и семантику

Прочитать [validation-rules.md](references/validation-rules.md) и применить все обязательные правила. Для каждой проблемы сохранить:

- источник и JSONPath/индекс;
- фактическое значение с безопасной маскировкой;
- ожидаемое правило;
- количество затронутых элементов;
- потенциальное влияние на расчёт;
- минимальный фрагмент доказательства.

Не считать клиентскую терпимость доказательством корректности API. Например, если клиент преобразует `usd` в `USD`, всё равно сообщить о нарушении регистра как о контрактной неточности.

### 5. Проверить валюты доказательно

1. Проверить, что код после `trim()` состоит ровно из трёх ASCII-букв.
2. Отдельно сообщить о пробелах, смешанном/нижнем регистре и невидимых Unicode-символах.
3. Сопоставить нормализованный код с актуальным авторитетным перечнем ISO 4217 либо документацией используемого провайдера курсов. Для текущей проверки получать актуальный источник, а не полагаться только на память.
4. Разделять выводы:
   - `подтверждённо неизвестный код` — отсутствует в выбранном авторитетном перечне;
   - `не поддерживается провайдером курса` — код может существовать, но курс недоступен;
   - `требует уточнения` — доказательств недостаточно.
5. Сохранять ссылку/название и дату проверки справочника. Не отправлять финансовые API-ключи сторонним сервисам.

### 6. Сопоставить источники

Сравнить только те аспекты, которые действительно должны быть согласованы:

- множество используемых валют;
- формат, точность и допустимый знак суммы;
- наличие очевидных точных дублей внутри и между источниками;
- временной срез, если ответы содержат даты;
- систематические различия регистра, пробелов и представления чисел.

Не объявлять одинаковые операции дублями только по сумме и валюте. Для уверенного вывода требовать идентификатор операции или достаточный набор совпадающих полей. Иначе помечать как гипотезу.

### 7. Классифицировать находки

Использовать уровни:

- **BLOCKER** — ответ нельзя надёжно прочитать или оба источника недоступны; расчёт невозможен.
- **HIGH** — данные могут вызвать исключение, неверную валютную конвертацию или существенное искажение суммы.
- **MEDIUM** — контракт нарушен, но текущий клиент способен компенсировать проблему; сохраняется риск для других потребителей.
- **LOW** — качество/единообразие данных ухудшено без текущего влияния на расчёт.
- **INFO** — наблюдение или рекомендация без подтверждённого дефекта.

Отдельно указывать уверенность: `высокая`, `средняя`, `низкая`. Не использовать эмоциональные или обвинительные формулировки. Писать «ответ содержит», а не «backend сломан».

### 8. Создать отчёт

Всегда создавать Markdown-отчёт по [report-template.md](references/report-template.md). По умолчанию сохранять его в согласованный пользователем каталог либо в текущий рабочий каталог с именем:

`finance-api-validation-YYYYMMDD-HHMMSSZ.md`

Требования к отчёту:

- писать короткими понятными фразами без канцелярита;
- укладываться по умолчанию в 250–500 слов и примерно одну страницу;
- использовать только короткие заголовки, абзацы и маркированные списки;
- не использовать таблицы, ASCII-рамки, псевдографику и декоративные разделители;
- не перечислять статистику по уровням серьёзности, если она не помогает понять результат;
- начинать с даты, API и простого итога: всё корректно, есть замечание или расчёт невозможен;
- кратко описывать каждый источник: доступность, число элементов и найденные проблемы;
- для каждой уникальной проблемы давать 1–2 фактических примера, влияние и конкретное исправление;
- группировать одинаковые дефекты, а не перечислять каждый JSONPath;
- добавлять технические пути, SHA-256, длительность, размер ответа и детали воспроизведения только при ошибке транспорта, спорном выводе или явном запросе пользователя;
- отделять подтверждённые дефекты от предположений;
- указывать, если проблем нет;
- не включать полные ответы API.

Считать подробные метаданные и хеши внутренними доказательствами. Не перегружать ими основной отчёт. После записи перечитать файл и проверить: нет секретов, нет незаполненных шаблонов, примеры существуют в снимке, ни одно предположение не выдано за факт.

## PDF

Создавать PDF только по запросу пользователя или если он явно нужен для передачи. Markdown остаётся источником истины.

1. Преобразовать тот же Markdown в аккуратный HTML/PDF доступным в окружении инструментом.
2. Не добавлять в PDF данные, отсутствующие в Markdown.
3. Использовать формат A4, короткие абзацы, читаемые переносы примеров и кликабельные ссылки, если инструмент поддерживает.
4. Проверить количество страниц, отсутствие пустых страниц, обрезанного текста, наложений и заменённых символов кириллицы.
5. Сохранить рядом как `finance-api-validation-YYYYMMDD-HHMMSSZ.pdf`.
6. Если надёжный PDF-инструмент недоступен, оставить проверенный Markdown и явно сообщить, что PDF не создан; не устанавливать production-зависимость ради отчёта.

## Контроль качества перед завершением

- Оба источника запрошены в рамках одного запуска либо причина исключения указана.
- Сырые значения проанализированы до нормализации.
- Валюты проверены без смешения «не существует» и «не поддерживается».
- Суммы не преобразованы молча и не округлены для анализа.
- Найдены и объяснены различия регистра, пробелов, типов и форматов.
- Все выводы подтверждены путём и минимальным фрагментом.
- Секреты и чувствительные данные отсутствуют во всех артефактах.
- Markdown перечитан; PDF, если создан, визуально проверен.
- Пользователю переданы пути к отчёту и снимкам либо указано, почему снимки не сохранены.

## Ограничения выводов

- Один снимок показывает состояние только в момент проверки, а не общую доступность API.
- Отсутствие проблемы в одном ответе не доказывает соблюдение контракта во всех ответах.
- Не назначать владельца дефекта без данных маршрутизации/архитектуры.
- Не рекомендовать клиенту постоянно компенсировать серверный дефект вместо исправления контракта.
